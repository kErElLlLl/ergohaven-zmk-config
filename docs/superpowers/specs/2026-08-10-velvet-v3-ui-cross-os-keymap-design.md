# Velvet v3 UI: кроссплатформенная (Mac/Windows/Linux) RU/EN раскладка

Дата: 2026-08-10
Статус: approved (design), реализация не начата

## Проблема

Клавиатура Velvet v3 UI используется на трёх системах: macOS, Windows, Linux.
Сейчас в репозитории два кеймапа для правой половины/qube:

- `config/velvet_v3_ui.keymap` — только английская раскладка, текущий "удобный"
  вариант пользователя (home row mods, mouse-layer через trackball, лэйауты
  nav/sym/adj/mouse/scroll/sniper).
- `config/velvet_v3_ui_ruen.keymap` — RU+EN с переключением языка через комбо
  (позиции 3+4) и попыткой унифицировать символы (`sym_en`/`sym_ru` +
  `&en`-макрос, временно переключающий язык ОС на английский, чтобы напечатать
  символ, которого нет в RU-раскладке).

Пользователь печатает кириллицей регулярно (не изредка), поэтому RU-слой
нужен полноценно. Требования:

1. Физически одна и та же клавиша должна давать один и тот же результат на
   всех трёх ОС (в первую очередь — шорткаты вроде Copy/Paste/Undo, которые на
   Mac висят на Cmd, а на Windows/Linux — на Ctrl).
2. Символы должны быть на тех же физических местах независимо от активной
   раскладки ОС (RU или EN) — это уже частично решено в `_ruen`, но завязано
   на Windows-специфичный хоткей прямого выбора языка (`Ctrl+Shift+1/2`).

Подключение: три отдельных Bluetooth-профиля, один на систему (`BT_SEL 0/1/2`).

## Что делаем и что не делаем

- Правим `config/velvet_v3_ui_ruen.keymap` — это уже подключённый в
  `build.yaml` bilingual-таргет для `velvet_v3_ui_right` и
  `velvet_v3_ui_qube`.
- `config/velvet_v3_ui.keymap` (EN-only) не трогаем — остаётся как есть.
- Nav-слой оставляем как в текущем `_ui.keymap`: без `Ctrl+←/→` word-jump.
  На Mac это системный шорткат переключения Spaces, а не word-jump (там это
  Option+←/→), поэтому бинд пришлось бы форкать по ОС отдельно от
  home-row-mod механизма. В текущей раскладке пользователя этой клавиши и так
  нет — это не потеря функциональности, а фиксация статус-кво. Можно добавить
  отдельным OS-aware комбо позже, если понадобится.
- Никакого рантайм-автоопределения ОС не будет (ZMK этого не может — нет
  обратного канала от хоста). Вместо этого OS-режим и BT-профиль
  переключаются одним и тем же действием пользователя.

## Архитектура

### Базовые слои: 4 вместо 2

Раньше: `en`, `ru`.
Станет: `en_pc`, `en_mac`, `ru_pc`, `ru_mac`.

`_mac`-варианты отличаются от `_pc` только свопом `LEFT_CONTROL`↔
`LEFT_COMMAND` и `RIGHT_CONTROL`↔`RIGHT_COMMAND` на home row mods (S/L —
control-позиция, F/J — command-позиция). `LEFT_ALT`/`RIGHT_ALT` не меняются —
Alt одинаков на всех трёх ОС. Всё остальное (буквы, thumb-row) идентично
внутри одной языковой пары.

**Важное ограничение, вскрывшееся уже после первой реализации**: пользователь
редактирует кеймапы через ZMK Keymap Editor (GUI-редактор поверх
`.keymap`-файлов), а он парсит devicetree-синтаксис напрямую, без прогона
через C-препроцессор. Параметризованные `#define`-макросы (`ROW2_EN(...)`,
именованные индексы слоёв типа `L_EN_PC`) редактор не резолвит — не может
сопоставить биндинг с behavior/параметрами и корректно перегенерировать файл.
Поэтому **вместо DRY-макросов используется буквальное дублирование строк**, а
номера слоёв — обычные литералы (`&mo 4`, `&to 1`), как и в исходных файлах
репозитория. `RU_CYRILLIC_*`-константы из `keys_ru.h` — это тоже `#define`,
но простые (без параметров) и уже использовались в обоих исходных кеймапах
до этой правки, так что с редактором не конфликтуют.

Итоговая идентичность между `_pc`/`_mac` вариантами (и между `ru_pc`/`ru_mac`,
которые дублируют друг друга целиком, поскольку кириллические ряды не могут
"провалиться" через `&trans` на несвязанный слой) проверяется скриптом
`scripts/check-keymap-layers.sh` — см. раздел «Тесты и проверки».

### Переключение хоста = переключение OS-режима (один шаг)

В `adj`-слое `&bt BT_SEL n` заменяется на три макроса:

```c
bt_mac: bindings = <&bt BT_SEL 0>, <&to L_EN_MAC>;
bt_win: bindings = <&bt BT_SEL 1>, <&to L_EN_PC>;
bt_lin: bindings = <&bt BT_SEL 2>, <&to L_EN_PC>;
```

`&to` — абсолютная установка слоя (не toggle), поэтому результат
детерминирован независимо от того, сколько раз до этого нажимали разные
OS-кнопки. Побочный эффект: при смене хоста язык всегда сбрасывается на EN
(сознательное упрощение — иначе пришлось бы либо дублировать RU/EN-состояние
для каждой из 3 систем, либо городить рантайм-branching, которого в ZMK нет).
Переключить обратно на RU после смены хоста — то же комбо, что и раньше,
стоимость — одно лишнее нажатие раз в сессию.

### Комбо переключения RU/EN — с учётом OS-режима

Комбо на позициях 3+4 должно попадать в правильный `_pc`/`_mac` вариант.
ZMK-комбо поддерживают `layers = <N>` — ограничение по активному слою, это и
используем вместо branching:

```c
cmbru_pc  { bindings = <&to L_RU_PC>;  key-positions = <3 4>; layers = <L_EN_PC>; }
cmbru_mac { bindings = <&to L_RU_MAC>; key-positions = <3 4>; layers = <L_EN_MAC>; }
cmben_pc  { bindings = <&to L_EN_PC>;  key-positions = <3 4>; layers = <L_RU_PC>; }
cmben_mac { bindings = <&to L_EN_MAC>; key-positions = <3 4>; layers = <L_RU_MAC>; }
```

## Символы независимо от RU/EN-раскладки

Механизм из `_ruen.keymap` сохраняется: `sym_en`/`sym_ru` — общие для
`_pc`/`_mac` (символьная раскладка не зависит от ОС, только от языка), плюс
`&en`-макрос для символов, которых физически нет в RU-раскладке (`{ } @ # $
~ ^ & | [ ] < >`): он на секунду переключает язык ОС на английский, таплает
символ и переключает обратно.

Меняется способ переключения языка ОС: вместо Windows-специфичного
`Ctrl+Shift+1/2` (прямой выбор языка) — единый **toggle**-хоткей **Ctrl+Space**
(дефолт для "Select next input source" на macOS, настраивается как toggle на
Windows и Linux). Поскольку языков всего два, toggle эквивалентен прямому
выбору — и не требует разного бинда на разных ОС, значит `to_ru`/`to_en`/
`en`-макрос остаются одним и тем же кодом без ветвления по ОС.

Инвариант, на который это завязано: пользователь переключает язык ОС
**только** через клавиатуру (комбо/макрос), никогда вручную через трей/
системное меню — иначе состояние "на какой ОС-раскладке мы сейчас" разъедется
между прошивкой и хостом, и toggle пойдёт не в ту сторону.

Пользователю нужно один раз в каждой ОС назначить `Ctrl+Space` на "переключить
источник ввода":
- macOS: уже дефолт (System Settings → Keyboard → Keyboard Shortcuts → Input
  Sources → Select next input source).
- Windows: Language bar / advanced key settings, либо PowerToys Keyboard
  Manager, если системный диалог не даёт задать произвольную комбинацию.
- Linux: ibus/fcitx — настройка trigger-хоткея.

## Тесты и проверки

1. **Компиляция.** Кеймап уже подключён в `build.yaml` → GitHub Actions
   (`build-user-config.yml`) соберёт прошивку при пуше/PR. Ловит синтаксис
   devicetree, неправильные индексы слоёв, дубли позиций в комбо.

2. **Скрипт подсчёта позиций** (`scripts/check-keymap-layers.sh`). Прогоняет
   кеймап через C-препроцессор (только ради `#include`/`RU_CYRILLIC_*` —
   собственных параметризованных макросов в файле больше нет, см. выше) и
   сверяет число `&`-биндингов в каждом layer-блоке — должно быть 46 (число
   клавиш платы) у всех слоёв. Ловит потерянную/задвоенную клавишу при
   копипасте ряда между `_pc`/`_mac` вариантами до прошивки.

3. **Ручной чек-лист** (три ОС, отдельным файлом, отмечается по ходу теста
   на живом железе):

   | Проверка | Mac | Windows | Linux |
   |---|---|---|---|
   | Copy/Paste/Cut/Undo/Redo/SelectAll/Save/Find — один и тот же палец | ☐ | ☐ | ☐ |
   | RU-буквы печатаются корректно (ЙЦУКЕН на месте) | ☐ | ☐ | ☐ |
   | Ctrl+Space переключает RU↔EN раскладку ОС | ☐ | ☐ | ☐ |
   | 12 "трудных" символов `{ } @ # $ ~ ^ & | [ ] < >` печатаются верно в RU-режиме | ☐ | ☐ | ☐ |
   | Переключение BT-профиля меняет Ctrl/Cmd и сбрасывает язык на EN | ☐ | ☐ | ☐ |
   | После смены хоста комбо RU/EN снова работает | ☐ | ☐ | ☐ |
